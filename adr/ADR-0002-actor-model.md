# ADR-0002: Actor モデルによるノード内並行制御

| 項目 | 内容 |
|---|---|
| ステータス | Accepted |
| 日付 | 2026-06-04 |
| 決定者 | アーキテクト |

---

## コンテキスト

ノード内で複数の並行処理が将来必要になる。

- ECS シミュレーション（CPU 集中・バッチ処理）
- Event Log への書き込み（I/O・シリアライズ）
- ノード間の通信（将来・ネットワーク I/O）
- メトリクス収集

これらを安全に並行実行する仕組みと、ECS（データ指向設計）との組み合わせ方を決定する必要があった。

---

## 検討した選択肢

### A: 共有状態 + Arc<RwLock<T>>

`Arc<RwLock<SimWorld>>` でノード内の状態を共有し、各処理が Lock を取得して変更する。

**メリット:**
- 実装が直感的
- 読み取りが多いワークロードでは RwLock が効率的

**デメリット:**
- 複数の Lock を順番に取得するとデッドロックのリスクがある
- Lock の競合が ECS のバッチ処理パフォーマンスを劣化させる
- テスト時に並行性バグを再現するのが困難
- Lock 境界が明示されないため AI による継続開発で競合を導入しやすい

### B: Actor モデル（tokio mpsc + task）

各責務を独立した Actor として実装し、Mailbox（mpsc チャンネル）経由でのみ通信する。  
外部 Actor フレームワーク（Actix 等）は使わず、tokio の primitive を直接使う。

**メリット:**
- Actor が自分のデータを所有するため、Lock が不要
- デッドロックが構造的に発生しない（Actor は循環して待機しない）
- テストが容易（メッセージの送受信を単体でテストできる）
- 将来の物理分散化で Actor 間通信がネットワーク越しになっても、
  インターフェース（Mailbox）が変わらない

**デメリット:**
- メッセージパッシングのオーバーヘッドがある
- 全ての操作が非同期になるため、単純な処理でもコードが複雑になりうる

### C: 外部 Actor フレームワーク（Actix 等）

成熟した Actor フレームワークを使用する。

**デメリット:**
- Actix は HTTP サーバー用途に最適化されており ECS との統合に余分な抽象層が生じる
- フレームワークの制約が設計の自由度を下げる
- AI が生成するコードがフレームワーク固有のパターンに依存しすぎる

---

## 決定

**Actor モデルを採用し、tokio の mpsc チャンネルで自前実装する（選択肢 B）**  
**ただし、Phase 0–1 では Actor を導入せず、Phase 2 から段階的に導入する**

---

## 根拠

ECS（データ指向・バッチ処理）と Actor（メッセージパッシング・疎結合）は
目的が異なる。組み合わせることで両者の利点を享受できる。

```
ECS  : 「何がどう変わるか」の計算（MovementSystem 等）
Actor: 「いつ・誰に通知するか」の調整（EventStore への書き込み等）
```

Actix を使わない理由:  
tokio の mpsc + task は Rust エコシステムで最も理解されたプリミティブであり、
AI が生成したコードのレビューが容易。フレームワーク固有の知識を必要としない。

Phase 0–1 で Actor を導入しない理由:  
Single Process の同期処理では Actor の利点（障害分離・非同期通信）が発揮されない。
`SimulationNode` の同期実装でドメインロジックを先に確立し、
Actor 化は Phase 2 の分散化と同時に行う。

---

## 影響

### 採用によって得られるもの

- Actor 境界が Lock 境界になるためデッドロックが構造的に排除される
- 将来の物理分散化で Actor 間通信をネットワーク越しに変えても
  ビジネスロジックへの変更が最小になる
- テストが「メッセージを送ってレスポンスを確認する」形に統一される

### 採用によって生じるトレードオフ

- 全操作が非同期になるため、コードの複雑性が増す
- Phase 2 移行時に `SimulationNode` の同期 API を非同期 Actor API に置き換える作業が必要

### この決定が強制する設計上の制約

```
- Actor はデータを Arc<Mutex<T>> で直接共有してはならない（CLAUDE.md FBD-004）
- Actor 間の通信は Mailbox（mpsc::Sender）経由のみ
- Actor の内部状態をテストで直接参照してはならない（メッセージ経由でテスト）
```

### Phase 2 で導入する Actor 一覧（予定）

```
SectorSimulatorActor : ECS World の所有と Tick 実行
EventStoreActor      : Event Log への Append
```
