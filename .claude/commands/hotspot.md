# /hotspot — git churn ベースのリファクタ対象選定＆改修

このスキルは「古いコード」ではなく **ホットスポット**
（変更頻度が高く、かつ複雑／規約違反が残っているファイル）を git 履歴から特定し、
上位 1 ファイルを選んで `/simplify` 相当のクリーンアップ＋テスト確認まで行う。

> **なぜ churn（変更頻度）か**
> 純粋な「経過時間（古さ）」はアンチシグナルである。長く変わっていないコードは
> 枯れて動いている可能性が高く、触るとリスクだけ負って得が小さい（Chesterton's Fence）。
> 一方、**頻繁に変更されているのに散らかっているコード**は「今後も触る場所」であり、
> ここを整えるのが最もペイする（Tornhill, *Your Code as a Crime Scene*）。
> `/simplify` が「直近の差分」を対象にするのに対し、本スキルは「履歴上の集積」を対象にする。

引数（任意）:
- 数値 = 集計するコミット数（既定: 300）。例: `/hotspot 150`
- ファイルパス = ランキングを飛ばしてそのファイルを直接改修対象にする。

---

## Phase 0 — ホットスポットを集計する

### Step 1: churn（変更頻度）ランキング

Bash で直近 N コミットのソース変更回数を集計する（`target/` や生成物は除外、
ソース拡張子のみ）。N は引数があればその値、なければ 300。

```bash
git log -n 300 --format= --name-only -- 'crates/**/*.rs' 'client/**/*.gd' \
  | grep -E '\.(rs|gd)$' | sort | uniq -c | sort -rn | head -20
```

### Step 2: 各上位ファイルの複雑度／規約シグナルを採る

churn 上位 ~12 ファイルについて、以下を採取してスコアを補正する。

- **規模**: 行数（`wc -l`）。大きいほど改修余地がある。
- **日本語コメント残存数**（CLAUDE.md §8 の英語化方針に未追従）:
  Grep ツール（ripgrep）で `\p{Han}|\p{Hiragana}|\p{Katakana}` を
  `output_mode: "count"` で数える。多いほど「触るとき英語化」の負債が大きい。
- **直近のバグ密度**: そのファイルを変更した `fix(` コミット数。
  `git log -n 300 --oneline --grep '^fix' -- <file> | wc -l`。
- **直近の変更理由**: `git log -n 5 --oneline -- <file>`（なぜホットかを説明するため）。

### Step 3: ランキングを提示する

churn を主、複雑度・規約残存・バグ密度を従としてホットスポット順に並べ、
次の形式で報告する（スコアは机上の相対値でよい）。

```
| 順位 | ファイル | churn | 行数 | JPコメント | fix数 | なぜホットか（直近の変更理由） |
|---|---|---|---|---|---|---|
```

そのうえで **改修を推奨する 1 ファイル** を理由つきで提示する。
推奨は「churn が高く、かつ複雑度／規約残存が大きい」ものを選ぶ。
ただし次は除外・降格する:
- 直近のコミットで `/simplify` 済み、または大規模リファクタ済みのファイル
- 役割上 churn が高いだけで散らかっていないファイル（例: `lib.rs` の re-export 集約、`mod.rs`）

引数でファイルが指定されている場合は Phase 0 を簡略化し、そのファイルを対象にする。

## Phase 1 — 対象 1 ファイルを確定する

ユーザーに改修対象を確認する（推奨ファイルでよいか、別ファイルにするか）。
**1 セッションで改修するのは 1 ファイルに限る**（差分を小さく保ち、レビュー可能にする）。

確定したら、改修方針を 3〜6 個の具体的な項目として宣言してから着手する。

---

## Phase 2 — 改修する（品質のみ・挙動は変えない）

`/simplify` と同じ 4 観点でクリーンアップする。**バグ探索はしない**（それは `/code-review`）。

- **Reuse**: 既存ヘルパーの再実装を共通化する。
- **Simplification**: 派生可能な状態・コピペ・深いネスト・デッドコードを削る。
- **Efficiency**: 毎 Tick / ホットパスの無駄な計算・重複ルックアップを削る。
- **Altitude**: 共有基盤への場当たり的な特殊化を、下層の一般化に置き換える。

加えて、このファイルを「触る」ので CLAUDE.md §8 に従い:
- **このファイル内の日本語コメントを英語に変換する**（一括変換はしない＝今触る範囲のみ）。

### ガードレール（このリポジトリ固有・必須）

- **Architecture Invariants（INV-001〜006）と Forbidden Changes（FBD-001〜009）を破らない。**
  特に Event Log は append-only（INV-001）、State は Event から再現可能（INV-002）、
  因果順序は論理 Tick（INV-005/FBD-003）を維持する。
- **挙動を変えない。** イベントのスキーマ・発行条件・Tick 処理順序を変える改修は
  本スキルの範囲外。必要なら ADR を起票して人間承認を得る（CLAUDE.md §1/§7）。
- **CLAUDE.md / docs/adr/ を自律的に書き換えない。**
- リスクが効果を上回る項目、差分が対象ファイルを大きく外れる項目は **見送り**、
  理由を添えて報告する（無理に直さない）。

### 検証

```bash
cargo test --workspace
```

ゼロエラーを確認する。`pub fn` を追加した場合は対応テストを用意する（FBD-007）。

- 変更があればコミットする（英語・Conventional Commits / docs/process/commit-convention.md）。
  例: `refactor(dawn-simulation): <file> のホットスポット整理（churn 上位）`
