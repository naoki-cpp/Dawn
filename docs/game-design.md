# Game Design

## 1. このドキュメントの目的

実装判断の根拠となるゲームデザイン方針を記録する。
「なぜこの機能を入れるか / 入れないか」を説明する文書である。

---

## 2. EVE Online から学ぶ

このプロジェクトは EVE Online の技術基盤を研究対象としているが、
ゲーム体験としての EVE の良い点・悪い点を理解した上で設計する。

### ✅ 活かすべき良い点

#### 行動に重みがある（Loss Aversion）

EVE では船を失うと本当に痛い。これが慎重な戦術判断を促し、
戦闘に緊張感を生む。

```
このプロジェクトへの応用:
  - 船が破壊されたら即復活できない設計
  - リスポーン時のペナルティ（装備リセット等）を検討する
  - 「死が怖い」設計が戦術的深みを生む
```

#### 意図的な 2 フェーズ戦闘設計

「ロックオン → 武器起動 → 射撃」という複数ステップが、
思考と判断を生む。

```
このプロジェクトへの応用（実装済み）:
  - Lock-on（右クリック） → F1 で武器起動 の 2 フェーズ
  - NPC は自動だがプレイヤーは明示的に操作する
```

#### フィッティングによる多様な戦術

同じ船でもフィッティング次第で役割が変わる（タンク / DPS / サポート）。

```
このプロジェクトへの応用（実装済み）:
  - Active / Passive モジュール区別
  - 船種ごとに異なる SlotLayout
  - 武器能力はモジュールのみで付与（ベースはゼロ）
```

#### Single Shard — 全員が同じ世界にいる意味

自分の行動が世界に影響する実感。記録に残る。

```
このプロジェクトの核（技術的使命）:
  - 分散シミュレーションの技術実証
  - Event Sourcing による完全な因果追跡
```

#### 役割分担（Asymmetric Roles）

タックラー（足止め） / DPS（火力） / ロジスティクス（修理）という非対称性が
小人数でも戦術的な深みを生む。

```
このプロジェクトへの応用（船種設計で活かす）:
  - フリゲート: 速い・ロック役・少スロット
  - クルーザー: バランス型
  - バトルシップ: 重い・高火力・多スロット
```

### Small Gang 思想 — 船種・フィッティング拡張の指針（非交渉的）

**理想とするゲーム体験を一言で言えば:**
EVE Online の small gang ロームのように、**ソロでも遊べるが、
10 人以下のチームで役割分担し連携することで真価を発揮する**システムである。

```
ソロ      : 1 隻でも独立して機能し、判断・操作を楽しめる
small gang: 少人数が異なる役割を持ち寄ることで、単独の合計を超える強さが生まれる
大規模    : 意図的にスコープ外（Anti-TiDi 同様、技術的にも思想的にも志向しない）
```

**EVE Online で最も避けたい失敗は「数が正義」である。**
ドクトリン艦隊——同型艦を数百隻並べて物量で押し切る戦術——は、
個人の判断力・フィッティングの工夫・連携の妙をすべて無価値にする。
これは「行動に重みを持たせる」という本ドキュメント冒頭の理念そのものへの裏切りであり、
**このプロジェクトが目指す体験の正反対**である。

```
EVE Online の現実: 数 × 平均スキル ≈ 戦闘の結果
                   個人の腕前もフィッティングの工夫も、数の差の前では誤差になる

このプロジェクトの理想: 役割の噛み合わせ × 個人の判断 ≈ 戦闘の結果
                       同数なら、より良く連携したチームが勝つ
                       数の優位は「線形に」勝率を上げてはならない
```

#### 「数を正義にしない」ための設計原則

船種・モジュール・戦闘システムを拡張する際、以下を満たすかどうかを判断基準にする。
満たさない設計（あるいは満たすことを難しくする設計）は採用しない。

```
原則A: 役割は「代替できないこと」によって定義される
  同じ役割の船を増やしても、戦力が単純加算されない設計にする。
  例: ロックには対象数の制限がある → ロック役を増やすことに上限的な価値しかない
      電子戦は対象を選んで無効化する → 同種の EW を重ねがけしても効果が頭打ちになる
  「同じ船を並べれば並べるだけ強い」という関係を作らないこと。

原則B: 連携は「単独ではできないこと」を可能にする
  タックル（足止め）→ DPS（処理）→ ロジ（回復）のように、
  ある役割の働きが別の役割の働きを「初めて意味のあるもの」にする設計を志向する。
  単独でも完結はするが、役割が噛み合うことで初めて生まれる結果を作る。

原則C: 個人の判断が常に介在する
  「放置すれば強い」「数を揃えれば自動的に勝てる」設計を避ける（FBD-009 採掘禁止の精神と同じ）。
  Capacitor のサイクル管理、ロックオンの2フェーズ、3層 HP のダメージタイプ相性など、
  既存の「常時 ON で勝ち」を崩す設計（ADR-0011 参照）を今後も拡張の基本姿勢とする。

原則D: 少人数で完結する戦術単位を想定する
  船種・スロット数・コストは「2〜10 隻のグループでの運用」を基準に設計する。
  「もっと大規模な艦隊が欲しくなる」方向ではなく、
  「この少人数編成で何ができるか」を深める方向に拡張する。
```

#### lore との関係（順序の確認）

`docs/lore/` はこの理想のゲームプレイに**物語的な意味づけを与えるもの**であり、
ゲームプレイを制限する制約ではない。

```
正しい順序: 「どんなプレイ体験を作りたいか」が先
            → それを実現する船種・モジュール・システムを設計する
            → その設計に説得力を与える lore を後から（または並行して）integrate する

避けるべき順序: 「lore がこう言っているから、この船はこういう性能でなければならない」
              → ゲームプレイがロアの辻褄合わせに従属してしまう
```

lore（`civilizations.md` の四勢力）は「誰が・なぜ・どう戦うか」という
動機と個性を与えるための資源として活用する。
ただし lore 側の記述が small gang 体験と矛盾する場合は、
ゲームプレイを優先し、lore 側の記述・歴史を修正する（lore は派生物であり、ゲーム体験が真実）。

#### ロール・ブレスト（船種・フィッティング拡張のたたき台）

small gang（2〜10 隻）で機能する非対称ロールの候補。
「代替不可能にする工夫」は、原則A（数を線形に強さへ変換しない）を
各ロールでどう実現するかの設計メモである。

| ロール | 機能 | 代替不可能にする工夫 |
|---|---|---|
| タックラー / インターセプター | 速度低下・Fold 妨害（離脱阻止）で敵を戦場に固定する。ロックオンとは独立した行動 | 速度低下・妨害効果は重ねがけしても効果が頭打ちになる（stacking penalty）→ 積み増すより他ロールと組み合わせる方が合理的になる（EWAR と同じ"無効化"ファミリー、原則A） |
| ストライカー（DPS） | 高火力・短時間で仕留める | 単独では持続力に欠け、回復役なしでは長期戦に弱い |
| ロジスティクス / 支援 | リモートリペア（シールド / 装甲） | 単独では何も壊せない。守る対象がいて初めて意味を持つ（原則B） |
| EWAR / ディスラプター | センサーダンパー・シグナルジャマーで敵の能力を無効化 | 同種の重ねがけは効果が頭打ちになる（原則A） |
| スカウト / 偵察 | 早期警戒・敵編成の察知、回避特化 | 戦闘力はほぼゼロだが、情報なしでは他ロールが機能しない |
| タンク | 高 HP・敵の攻撃を一身に引き受ける | 火力が低く、他ロールに攻撃機会を「与える」ことでのみ価値が生まれる |

#### 勢力との対応（civilizations.md ベース）— 「全ロール + 得意分野ボーナス」モデル

EVE Online の種族設計を参考にする：種族ごとに「持てるロール」が
分かれているわけではない。アマーにもタックラーは存在し、
ミンマターにもタンク特化のフィッティングは組める。違うのは
「どう実現するか」の質感と、得意分野を後押しするボーナスである。

これに倣い、**全勢力が全ロールの船を最低限持つ**ことを前提とする。

```
理由:
  - 「この勢力を選ぶと特定のロールしか遊べない」状態を避ける
    （同じ勢力のプレイヤー同士でも多様な small gang 編成を組めるようにする）
  - 一方で「勢力ごとの個性」は、得意分野への "ロールボーナス" で表現する
    （例: Compact のロジ艦は repair 効率に補正がつく、
          Nael のタンク艦は特定条件下で装甲/シールド値に補正がつく）
  - ボーナスは「その勢力ならではの強み」であり、
    「その勢力以外ではできないこと」ではない
    → 多様性を損なわず、個性は保たれる
```

各勢力の signature（得意分野）は、その軍事思想・社会構造（`docs/lore/civilizations.md`）
から実際にゲームメカニクスへ落とし込めるものだけを選ぶ。
lore に書かれていても現在のシステムで表現できないもの
（例: Voral Drift の「地形戦術」── Sector に地形概念は存在しない）は
signature から外し、表現可能な側面（フィッティングの改造文化、機動力）に置き換える。

| 勢力 | 全ロールの船を持つ（baseline） | signature（ロールボーナスが付く分野） |
|---|---|---|
| Kaerath Compact | ✅ | ロジスティクス（repair 効率）、組織的フィッティング（標準構成の安定性） |
| Voral Drift | ✅ | タックラー（機動力）、フィッティングの多様性（改造文化による高い構成自由度） |
| Tharren Seekers | ✅ | スカウト（索敵範囲）、EWAR（気脈感知由来のセンサー性能） |
| Nael Sanctuary | ✅ | タンク（防衛特化の装甲/シールド補正）、早期警戒（自陣営内での索敵ボーナス） |

> **注意:** Nael Sanctuary は「攻撃的な遠征軍を持たない」が、
> 「少数精鋭の防衛部隊」（civilizations.md）を持つため非武装ではない。
> 防衛特化のタンク・索敵船にボーナスが乗る、という解釈で船種設計を進める。

#### ロールボーナスの実装方針（將来の `data/*.toml` 拡張のメモ）

```
ロールボーナスは StatDelta / ShipBaseStats のレベルで表現できる
（既存の Fitting システムの延長線上にあり、新しい概念を必要としない）。

例（イメージ。実数値はバランス調整で決定する）:
  Kaerath Compact 製のロジ巡洋艦
    → 同型の他勢力ロジ艦より repair モジュールの効果が高い
  Nael Sanctuary 製のタンクフリゲート
    → 同型の他勢力タンク艦より装甲 / シールド最大値が高いが、速度は低い

これにより「勢力を選ぶ」ことは「使える戦術の幅を狭める」ことではなく
「得意分野の方向性を選ぶ」ことになる。
```

### ❌ 避けるべき悪い点

#### Time Dilation（TiDi）

大規模戦でゲームが 10 倍スローになる。体験が壊れる。

```
このプロジェクトの対応（非交渉的）:
  → INV-TIDI: Tick 速度は常に一定。
    負荷超過は Sector 入場制限で対処し、Tick を遅らせない。
```

#### 待機時間が多い

ゲート間の移動・スキルトレーニング・製造待ちなど
「待つだけ」のコンテンツが体験を損なう。

```
このプロジェクトの対応:
  - アクティブな操作が常に価値を持つ設計にする
  - パッシブなスキルトレーニングは実装しない
```

#### 初期学習コストが高すぎる

「最初の船を失うのは説明不足のせい」という批判がある。

```
このプロジェクトの対応（進行中）:
  - HP バー・モジュール状態・速度を常時 HUD に表示
  - F1〜F8 のキーバインドを明示
  - シンプルな操作から順番に機能を追加する方針
```

#### Blob 戦争（数が正義）

最大の艦隊が常に勝つ。個人スキルの意味が薄れる。

```
このプロジェクトの対応:
  - 10 人以下の small gang を中核に据え、個人の判断と連携が活きる戦場設計
  - 「数が線形に強さへ変換されない」設計を船種・モジュールの大前提とする
    （詳細な設計原則は §2「Small Gang 思想」参照）
  - 大規模化は Anti-TiDi インフラが整ってから検討（Phase 8）。
    ただし大規模化後も「数が正義」にはしない。
```

#### 情報過多 / UI の複雑さ

新規が圧倒される巨大な UI。

```
このプロジェクトの対応:
  - HUD は段階的に拡張する（現状: HP / 速度 / ロック / モジュール）
  - Cycle ごとに 1 機能ずつ追加する方針
```

## 3. このプロジェクトの優位性

| EVE Online の問題 | このプロジェクトの機会 |
|---|---|
| TiDi（時間停止）| Anti-TiDi を技術的保証として差別化できる |
| 戦闘の記録が残らない | Event Sourcing で全戦闘が完全に Replay 可能 → 観戦・検証機能 |
| 大艦隊では個人が霞む | 小規模（〜100 隻）に特化し個人の判断が活きる |
| 待機時間 | Tick は常に一定速。リアルタイムのみ |

## 4. 将来検討する機能（優先順位付き）

### 🔴 近い将来（ゲームバランスの核）

#### Capacitor（エネルギー管理）

Active モジュールが Cap を消費する。Cap が切れると武器が使えなくなる。
「全モジュールを常時 ON にすれば勝ち」にならないバランス調整機能。

```
設計イメージ:
  ShipStatsComp.max_cap, current_cap
  StatDelta.cap_usage_add（各モジュールの Cap 消費）
  Cap は毎 Tick わずかに回復する
  Cap = 0 → Active モジュールを起動できない
```

#### Shield リチャージ（非対称 HP 回復）

Shield は時間で回復する（Armor / Hull は回復しない）。
この非対称性が「今逃げるか、押し切るか」の判断を生む。

```
設計イメージ:
  毎 Tick: current_shield = min(max_shield, current_shield + recharge_rate)
  recharge_rate は ShipTypeDefinition で定義
  ShieldRechargedイベントは不要（派生状態）、Replay は recharge_rate × ticks で計算
```

### 🟡 中長期（戦術的深みの拡張）

#### ダメージタイプと耐性

EM / Thermal / Kinetic / Explosive の 4 タイプと、各 HP 層への耐性。
「この船にはこの武器が有効」という相性システム。

```
設計イメージ:
  DamageType enum { EM, Thermal, Kinetic, Explosive }
  ShipBaseStats に resistances: Resistances フィールド
  WeaponFired に damage_type を追加
  実ダメージ = damage × (1 - resistance[damage_type])
```

#### リスポーン

破壊後に一定時間後に復帰できる仕組み。
ペナルティ（装備リセット or クールタイム）で「死が怖い」を維持しつつ、
プレイを継続できる。

```
設計イメージ:
  RespawnCommand → 新しい ShipTypeId で spawn_player_ship
  プレイヤーは同じ PlayerId を維持（ship_id のみ変わる）
  フリゲートから始まるリスポーン（装備なし）
```

#### 陣営（Faction）

プレイヤーが陣営を選び、敵対陣営の NPC・プレイヤーと戦う。
「誰と戦うか」の文脈が生まれ、Single Shard の意味が深まる。

```
設計イメージ:
  FactionId を ShipSpawned / PlayerId と紐付ける
  LockSystem: 同一陣営はロック不可
  陣営ポイントで進行度を追跡
```

### 🟢 遠い将来（EVE らしさの完成）

- **Warp**: `WarpStarted / WarpFinished` イベント（ADR-0008 で例示済み）
- **Drone**: 船から展開する無人機
- **Logi（修理支援）**: 他の船の Shield を修復するモジュール
- **Tackler（足止め）**: 速度・ワープを阻害するモジュール（Web / Scram）

## 5. 実装しない機能（スコープ外）

### スキルポイントは実装しない（非交渉的）

EVE Online のスキルポイント制は**時代遅れの機能**である。

```
問題:
  ゲームの上手さに関係なく、ゲーム時間（またはリアルマネー）の投資量によって
  船の性能・装備の選択肢が変わる。

  具体的に何が起きるか:
    - 1年プレイしたベテランは、どれほど上手い新規プレイヤーでも
      純粋なスタット差で圧倒できる
    - スキルトレーニングを加速するため課金する仕組みが生まれる
    - 「今日から始めた人」と「3年前から始めた人」が公平に戦えない

  これは公平感（Perceived Fairness）を根本から損なう。

このプロジェクトの方針:
  ✓ 全プレイヤーは同じ船・モジュールを最初から使える
  ✓ 強さの差は「どの装備を選んだか」「どう戦ったか」のみ
  ✓ ゲーム時間・課金額は性能に影響しない
```

この原則は**いかなる理由があっても変更しない**。
「やり込み要素」「プレイヤーの成長感」を理由に導入を提案されても実装しない。

代わりに「成長感」を与える方法：
- フィッティングの理解が深まること自体が成長
- 戦闘経験から戦術が洗練されること
- 別の船種・ロールを試すこと

---

### 採掘は実装しない（非交渉的）

EVE Online における採掘は**放置コンテンツ**であり、ゲームプレイとは言い難い。

```
問題:
  採掘とは「採掘レーザーを起動して放置する」行為である。
  プレイヤーが能動的に判断・操作する余地がほとんどない。

  EVE コミュニティでは採掘者は「無力な標的」として語られる。
  これは採掘者自身のコンテンツではなく、
  採掘者を狙う海賊側のコンテンツとして機能している。

  つまり「採掘している人はゲームをしていない」。

このプロジェクトの方針（§6 の設計原則に基づく）:
  「その機能は、プレイヤーが意図的な判断を下す機会を増やすか？」
  → 採掘は No。実装しない。
```

資源・経済が必要になった場合の代替アプローチ（将来の検討のみ）：
- アクティブな操作が必要な「スキャニング」で資源場所を発見
- 発見した資源をめぐる戦闘が主コンテンツ（放置採掘ではなく争奪戦）
- ただしこれも現時点ではスコープ外

## 6. EVE Frontier から学ぶ

EVE Frontier は EVE Online の後継とも言えるプロジェクトであり、
EVE Online の設計を批判的に再解釈している点でこのプロジェクトにも示唆がある。

### 参考になる設計思想

#### 「開発者は舞台だけ提供する」という哲学

```
EVE Frontier: NPCクエストを排除。プレイヤーが互いのコンテンツになる。
              世界のルールと物理だけ開発者が作り、
              その中で何が起きるかはプレイヤーが決める。
```

このプロジェクトとの共鳴：
- Event Sourcing = 「何が起きたか」の完全な記録
  → プレイヤーの行動履歴が世界の歴史になる
- Single Shard = 全員が同じ世界にいる
  → プレイヤーが互いにコンテンツを作り合える
- Anti-TiDi = 世界は常にリアルタイムで動く
  → 「今ここで起きていること」に意味がある

```
このプロジェクトへの応用:
  NPC の役割 = 「プレイヤーがいない間の世界の動き」を作ること
  NPC はチュートリアル相手・世界に活気を与える存在であり、
  プレイヤーの真の脅威は他のプレイヤーであるべき
```

#### Smart Assemblies（プログラマブルなゲームオブジェクト）

EVE Frontier ではプレイヤーがゲームオブジェクトにロジックを書き込める。
例: 「このドアは XXX コープのメンバーしか通れない」

```
このプロジェクトへの示唆（将来の参考）:
  モジュールの効果が固定値（StatDelta）だけでなく
  条件付きで発動する仕組みへの伏線
  例: 「シールドが50%以下のとき自動で Shield Booster をオンにする」
  → 現状のフィッティング設計はこれを拡張できる構造になっている
```

#### 深刻な死のペナルティ

EVE Online よりさらに厳しい損失設計。「何もかも失う可能性がある」緊張感。

```
このプロジェクトへの応用:
  リスポーン設計で活かす。
  即時復帰より「失うものがある」設計が戦術的判断を生む。
  → docs/game-design.md §4 リスポーン設計参照
```

### 採用しない要素

#### ブロックチェーン / NFT によるアセット所有

EVE Frontier はアセット所有にブロックチェーンを使う。

```
このプロジェクトでは採用しない。理由:
  Event Sourcing がすでに「改竄不可能な記録」を提供している。
  ブロックチェーンはその役割と重複し、複雑さを加えるだけでメリットがない。
  「誰が何をしたか」の完全な記録は Event Log が担保する。
```

#### サバイバル要素（燃料・食料・熱管理）

EVE Frontier はサバイバルゲーム的な資源管理要素を持つ。

```
このプロジェクトでは採用しない。理由:
  「管理のための管理」になりやすく、
  §6 の設計原則「意図的な判断を増やすか？」に反する可能性が高い。
  採掘と同様に「放置 or ルーティン作業化」するリスクがある。
```

## 7. 設計上の中心的な問い

新機能を検討するとき、常にこの問いに戻る：

> **「その機能は、プレイヤーが意図的な判断を下す機会を増やすか？」**

Yes → 候補になりうる
No  → 採用しない

EVE Online のすべての良い点はこの問いへの Yes から生まれている。
TiDi / 待機時間のような悪い点はこの問いへの No から生まれている。
