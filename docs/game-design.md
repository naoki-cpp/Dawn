# Game Design

## 1. このドキュメントの目的

実装判断の根拠となるゲームデザイン方針を記録する。
「なぜこの機能を入れるか / 入れないか」を説明する文書である。

---

## 2. EVE Online から学ぶ

このプロジェクトは EVE Online の技術基盤を研究対象としているが、
ゲーム体験としての EVE の良い点・悪い点を理解した上で設計する。

### ✅ 活かすべき良い点

#### 行動に重みがある（Loss Aversion）

EVE では船を失うと本当に痛い。これが慎重な戦術判断を促し、
戦闘に緊張感を生む。

```
このプロジェクトへの応用:
  - 船が破壊されたら即復活できない設計
  - リスポーン時のペナルティ（装備リセット等）を検討する
  - 「死が怖い」設計が戦術的深みを生む
```

#### 意図的な 2 フェーズ戦闘設計

「ロックオン → 武器起動 → 射撃」という複数ステップが、
思考と判断を生む。

```
このプロジェクトへの応用（実装済み）:
  - Lock-on（右クリック） → F1 で武器起動 の 2 フェーズ
  - NPC は自動だがプレイヤーは明示的に操作する
```

#### フィッティングによる多様な戦術

同じ船でもフィッティング次第で役割が変わる（タンク / DPS / サポート）。

```
このプロジェクトへの応用（実装済み）:
  - Active / Passive モジュール区別
  - 船種ごとに異なる SlotLayout
  - 武器能力はモジュールのみで付与（ベースはゼロ）
```

#### Single Shard — 全員が同じ世界にいる意味

自分の行動が世界に影響する実感。記録に残る。

```
このプロジェクトの核（技術的使命）:
  - 分散シミュレーションの技術実証
  - Event Sourcing による完全な因果追跡
```

#### 役割分担（Asymmetric Roles）

タックラー（足止め） / DPS（火力） / ロジスティクス（修理）という非対称性が
小人数でも戦術的な深みを生む。

```
このプロジェクトへの応用（船種設計で活かす）:
  - フリゲート: 速い・ロック役・少スロット
  - クルーザー: バランス型
  - バトルシップ: 重い・高火力・多スロット
```

---

### ❌ 避けるべき悪い点

#### Time Dilation（TiDi）

大規模戦でゲームが 10 倍スローになる。体験が壊れる。

```
このプロジェクトの対応（非交渉的）:
  → INV-TIDI: Tick 速度は常に一定。
    負荷超過は Sector 入場制限で対処し、Tick を遅らせない。
```

#### 待機時間が多い

ゲート間の移動・スキルトレーニング・製造待ちなど
「待つだけ」のコンテンツが体験を損なう。

```
このプロジェクトの対応:
  - アクティブな操作が常に価値を持つ設計にする
  - パッシブなスキルトレーニングは実装しない
```

#### 初期学習コストが高すぎる

「最初の船を失うのは説明不足のせい」という批判がある。

```
このプロジェクトの対応（進行中）:
  - HP バー・モジュール状態・速度を常時 HUD に表示
  - F1〜F8 のキーバインドを明示
  - シンプルな操作から順番に機能を追加する方針
```

#### Blob 戦争（数が正義）

最大の艦隊が常に勝つ。個人スキルの意味が薄れる。

```
このプロジェクトの対応:
  - 10〜100 隻スケールに特化し、個人の判断が活きる戦場設計
  - 大規模化は Anti-TiDi インフラが整ってから検討（Phase 8）
```

#### 情報過多 / UI の複雑さ

新規が圧倒される巨大な UI。

```
このプロジェクトの対応:
  - HUD は段階的に拡張する（現状: HP / 速度 / ロック / モジュール）
  - Cycle ごとに 1 機能ずつ追加する方針
```

---

## 3. このプロジェクトの優位性

| EVE Online の問題 | このプロジェクトの機会 |
|---|---|
| TiDi（時間停止）| Anti-TiDi を技術的保証として差別化できる |
| 戦闘の記録が残らない | Event Sourcing で全戦闘が完全に Replay 可能 → 観戦・検証機能 |
| 大艦隊では個人が霞む | 小規模（〜100 隻）に特化し個人の判断が活きる |
| 待機時間 | Tick は常に一定速。リアルタイムのみ |

## 4. 将来検討する機能（優先順位付き）

### 🔴 近い将来（ゲームバランスの核）

#### Capacitor（エネルギー管理）

Active モジュールが Cap を消費する。Cap が切れると武器が使えなくなる。
「全モジュールを常時 ON にすれば勝ち」にならないバランス調整機能。

```
設計イメージ:
  ShipStatsComp.max_cap, current_cap
  StatDelta.cap_usage_add（各モジュールの Cap 消費）
  Cap は毎 Tick わずかに回復する
  Cap = 0 → Active モジュールを起動できない
```

#### Shield リチャージ（非対称 HP 回復）

Shield は時間で回復する（Armor / Hull は回復しない）。
この非対称性が「今逃げるか、押し切るか」の判断を生む。

```
設計イメージ:
  毎 Tick: current_shield = min(max_shield, current_shield + recharge_rate)
  recharge_rate は ShipTypeDefinition で定義
  ShieldRechargedイベントは不要（派生状態）、Replay は recharge_rate × ticks で計算
```

### 🟡 中長期（戦術的深みの拡張）

#### ダメージタイプと耐性

EM / Thermal / Kinetic / Explosive の 4 タイプと、各 HP 層への耐性。
「この船にはこの武器が有効」という相性システム。

```
設計イメージ:
  DamageType enum { EM, Thermal, Kinetic, Explosive }
  ShipBaseStats に resistances: Resistances フィールド
  WeaponFired に damage_type を追加
  実ダメージ = damage × (1 - resistance[damage_type])
```

#### リスポーン

破壊後に一定時間後に復帰できる仕組み。
ペナルティ（装備リセット or クールタイム）で「死が怖い」を維持しつつ、
プレイを継続できる。

```
設計イメージ:
  RespawnCommand → 新しい ShipTypeId で spawn_player_ship
  プレイヤーは同じ PlayerId を維持（ship_id のみ変わる）
  フリゲートから始まるリスポーン（装備なし）
```

#### 陣営（Faction）

プレイヤーが陣営を選び、敵対陣営の NPC・プレイヤーと戦う。
「誰と戦うか」の文脈が生まれ、Single Shard の意味が深まる。

```
設計イメージ:
  FactionId を ShipSpawned / PlayerId と紐付ける
  LockSystem: 同一陣営はロック不可
  陣営ポイントで進行度を追跡
```

### 🟢 遠い将来（EVE らしさの完成）

- **Warp**: `WarpStarted / WarpFinished` イベント（ADR-0008 で例示済み）
- **Drone**: 船から展開する無人機
- **Logi（修理支援）**: 他の船の Shield を修復するモジュール
- **Tackler（足止め）**: 速度・ワープを阻害するモジュール（Web / Scram）

## 5. 実装しない機能（スコープ外）

### スキルポイントは実装しない（非交渉的）

EVE Online のスキルポイント制は**時代遅れの機能**である。

```
問題:
  ゲームの上手さに関係なく、ゲーム時間（またはリアルマネー）の投資量によって
  船の性能・装備の選択肢が変わる。

  具体的に何が起きるか:
    - 1年プレイしたベテランは、どれほど上手い新規プレイヤーでも
      純粋なスタット差で圧倒できる
    - スキルトレーニングを加速するため課金する仕組みが生まれる
    - 「今日から始めた人」と「3年前から始めた人」が公平に戦えない

  これは公平感（Perceived Fairness）を根本から損なう。

このプロジェクトの方針:
  ✓ 全プレイヤーは同じ船・モジュールを最初から使える
  ✓ 強さの差は「どの装備を選んだか」「どう戦ったか」のみ
  ✓ ゲーム時間・課金額は性能に影響しない
```

この原則は**いかなる理由があっても変更しない**。
「やり込み要素」「プレイヤーの成長感」を理由に導入を提案されても実装しない。

代わりに「成長感」を与える方法：
- フィッティングの理解が深まること自体が成長
- 戦闘経験から戦術が洗練されること
- 別の船種・ロールを試すこと

---

### その他スコープ外

CLAUDE.md §1 に準拠。以下は EVE に存在するがこのプロジェクトでは実装しない：

```
× 市場・経済システム
× キャラクター育成・スキルポイント（上記参照）
× 製造・採掘（Cycle N で再検討可能）
× インベントリ
× 課金・PLEX
× グラフィックスエンジン外部依存
```

## 6. 設計上の中心的な問い

新機能を検討するとき、常にこの問いに戻る：

> **「その機能は、プレイヤーが意図的な判断を下す機会を増やすか？」**

Yes → 候補になりうる
No  → 採用しない

EVE Online のすべての良い点はこの問いへの Yes から生まれている。
TiDi / 待機時間のような悪い点はこの問いへの No から生まれている。
