# Game Design

## 1. このドキュメントの目的

実装判断の根拠となるゲームデザイン方針を記録する。
「なぜこの機能を入れるか / 入れないか」を説明する文書である。

---

## 2. EVE Online から学ぶ

このプロジェクトは EVE Online の技術基盤を研究対象としているが、
ゲーム体験としての EVE の良い点・悪い点を理解した上で設計する。

### ✅ 活かすべき良い点

#### 行動に重みがある（Loss Aversion）

EVE では船を失うと本当に痛い。これが慎重な戦術判断を促し、
戦闘に緊張感を生む。

```
このプロジェクトへの応用:
  - 船が破壊されたら即復活できない設計
  - リスポーン時のペナルティ（装備リセット等）を検討する
  - 「死が怖い」設計が戦術的深みを生む
```

#### 意図的な 2 フェーズ戦闘設計

「ロックオン → 武器起動 → 射撃」という複数ステップが、
思考と判断を生む。

```
このプロジェクトへの応用（実装済み）:
  - Lock-on（右クリック） → F1 で武器起動 の 2 フェーズ
  - NPC は自動だがプレイヤーは明示的に操作する
```

#### フィッティングによる多様な戦術

同じ船でもフィッティング次第で役割が変わる（タンク / DPS / サポート）。

```
このプロジェクトへの応用（実装済み）:
  - Active / Passive モジュール区別
  - 船種ごとに異なる SlotLayout
  - 武器能力はモジュールのみで付与（ベースはゼロ）
```

#### Single Shard — 全員が同じ世界にいる意味

自分の行動が世界に影響する実感。記録に残る。

```
このプロジェクトの技術的土台（＝競争優位 / ADR-0016）:
  - 分散シミュレーション基盤（EVE が TiDi で諦めた大規模リアルタイム性）
  - Event Sourcing による完全な因果追跡
```

#### 役割分担（Asymmetric Roles）

タックラー（足止め） / DPS（火力） / ロジスティクス（修理）という非対称性が
小人数でも戦術的な深みを生む。

```
このプロジェクトへの応用（船種設計で活かす）:
  - フリゲート: 速い・ロック役・少スロット
  - クルーザー: バランス型
  - バトルシップ: 重い・高火力・多スロット
```

### Small Gang 思想 — 船種・フィッティング拡張の指針（非交渉的）

**理想とするゲーム体験を一言で言えば:**
EVE Online の small gang ロームのように、**ソロでも遊べるが、
10 人以下のチームで役割分担し連携することで真価を発揮する**システムである。

```
ソロ      : 1 隻でも独立して機能し、判断・操作を楽しめる
small gang: 少人数が異なる役割を持ち寄ることで、単独の合計を超える強さが生まれる
大規模    : ADR-0016 で最終ゴールに格上げ（柱①: TiDi の無い大規模リアルタイム戦闘）。
            ただし段階的に積む（solo/small gang の手触りを核に、そこから拡張）。
            負荷は 分割 → LoD → 局所 TiDi の順で捌く（ADR-0018）
```

**EVE Online で最も避けたい失敗は「数が正義」である。**
ドクトリン艦隊——同型艦を数百隻並べて物量で押し切る戦術——は、
個人の判断力・フィッティングの工夫・連携の妙をすべて無価値にする。
これは「行動に重みを持たせる」という本ドキュメント冒頭の理念そのものへの裏切りであり、
**このプロジェクトが目指す体験の正反対**である。

```
EVE Online の現実: 数 × 平均スキル ≈ 戦闘の結果
                   個人の腕前もフィッティングの工夫も、数の差の前では誤差になる

このプロジェクトの理想: 役割の噛み合わせ × 個人の判断 ≈ 戦闘の結果
                       同数なら、より良く連携したチームが勝つ
                       数の優位は「線形に」勝率を上げてはならない
```

#### 「数を正義にしない」ための設計原則

船種・モジュール・戦闘システムを拡張する際、以下を満たすかどうかを判断基準にする。
満たさない設計（あるいは満たすことを難しくする設計）は採用しない。

```
原則A: 役割は「代替できないこと」によって定義される
  同じ役割の船を増やしても、戦力が単純加算されない設計にする。
  例: ロックには対象数の制限がある → ロック役を増やすことに上限的な価値しかない
      電子戦は対象を選んで無効化する → 同種の EW を重ねがけしても効果が頭打ちになる
  「同じ船を並べれば並べるだけ強い」という関係を作らないこと。

原則B: 連携は「単独ではできないこと」を可能にする
  タックル（足止め）→ DPS（処理）→ ロジ（回復）のように、
  ある役割の働きが別の役割の働きを「初めて意味のあるもの」にする設計を志向する。
  単独でも完結はするが、役割が噛み合うことで初めて生まれる結果を作る。

原則C: 個人の判断が常に介在する
  「放置すれば強い」「数を揃えれば自動的に勝てる」設計を避ける（FBD-009 採掘禁止の精神と同じ）。
  Capacitor のサイクル管理、ロックオンの2フェーズ、3層 HP のダメージタイプ相性など、
  既存の「常時 ON で勝ち」を崩す設計（ADR-0011 参照）を今後も拡張の基本姿勢とする。

原則D: 少人数で完結する戦術単位を想定する
  船種・スロット数・コストは「2〜10 隻のグループでの運用」を基準に設計する。
  「もっと大規模な艦隊が欲しくなる」方向ではなく、
  「この少人数編成で何ができるか」を深める方向に拡張する。
```

#### lore との関係（順序の確認）

`docs/lore/` はこの理想のゲームプレイに**物語的な意味づけを与えるもの**であり、
ゲームプレイを制限する制約ではない。

```
正しい順序: 「どんなプレイ体験を作りたいか」が先
            → それを実現する船種・モジュール・システムを設計する
            → その設計に説得力を与える lore を後から（または並行して）integrate する

避けるべき順序: 「lore がこう言っているから、この船はこういう性能でなければならない」
              → ゲームプレイがロアの辻褄合わせに従属してしまう
```

lore（`civilizations.md` の四勢力）は「誰が・なぜ・どう戦うか」という
動機と個性を与えるための資源として活用する。
ただし lore 側の記述が small gang 体験と矛盾する場合は、
ゲームプレイを優先し、lore 側の記述・歴史を修正する（lore は派生物であり、ゲーム体験が真実）。

#### ロール・ブレスト（船種・フィッティング拡張のたたき台）

small gang（2〜10 隻）で機能する非対称ロールの候補。
「代替不可能にする工夫」は、原則A（数を線形に強さへ変換しない）を
各ロールでどう実現するかの設計メモである。

| ロール | 機能 | 代替不可能にする工夫 |
|---|---|---|
| タックラー / インターセプター | 速度低下・Fold 妨害（離脱阻止）で敵を戦場に固定する。ロックオンとは独立した行動 | 速度低下・妨害効果は重ねがけしても効果が頭打ちになる（stacking penalty）→ 積み増すより他ロールと組み合わせる方が合理的になる（EWAR と同じ"無効化"ファミリー、原則A） |
| アンチサポート（中型・制圧） | タックラー/EWAR など軽量で足の速い敵を狩り、味方のスナイパー・タックラーが仕事をできる「場」を作る。中型艦の機動力とそこそこの火力で前線を整理する | 軽量級を狩るだけでは戦況を決められず、重量級を削るスナイパーがいなければ勝ちきれない。両者を繋ぐ中継ぎとして初めて機能する（原則A・B：スナイパー/タックラー/ロジ各役の働きを成立させる前提条件になる） |
| スナイパー（DPS） | 長射程から高火力を一方的に浴びせ、近づかれる前に仕留める | 単独では持続力に欠け、近距離に踏み込まれると弱い。回復役・タックラーの援護なしでは長期戦に弱い |
| ロジスティクス / 支援 | リモートリペア（シールド / 装甲） | 単独では何も壊せない。守る対象がいて初めて意味を持つ（原則B） |
| EWAR / ディスラプター | センサーダンパー・シグナルジャマーで敵の能力を無効化 | 同種の重ねがけは効果が頭打ちになる（原則A） |
| スカウト / 偵察 | 早期警戒・敵編成の察知、回避特化 | 戦闘力はほぼゼロだが、情報なしでは他ロールが機能しない |
| タンク | 高 HP・敵の攻撃を一身に引き受ける | 火力が低く、他ロールに攻撃機会を「与える」ことでのみ価値が生まれる |

> **アンチサポートの船種基準**: Cruiser クラス（Frigate ほど打たれ弱くなく、Battleship ほど鈍重でない）
> を基本とする。軽量級を狩りきれる機動力と、中距離での継戦に耐えるタフさの両立が要件であり、
> この立ち位置は Frigate/Battleship では代替できない（原則A）。
>
> **ロールの依存連鎖**: タックラーが作った隙をアンチサポートが拡大し、
> スナイパーが仕留める。ロジスティクスはこの連鎖が壊れないよう支える。
> 一つのロールだけを増やしても連鎖は完成しない — これが「数を積むだけでは勝てない」を
> 構造的に保証する（Small Gang 思想の核）。

#### 勢力との対応（civilizations.md ベース）— 「全ロール + 得意分野ボーナス」モデル

EVE Online の種族設計を参考にする：種族ごとに「持てるロール」が
分かれているわけではない。アマーにもタックラーは存在し、
ミンマターにもタンク特化のフィッティングは組める。違うのは
「どう実現するか」の質感と、得意分野を後押しするボーナスである。

これに倣い、**全勢力が全ロールの船を最低限持つ**ことを前提とする。

```
理由:
  - 「この勢力を選ぶと特定のロールしか遊べない」状態を避ける
    （同じ勢力のプレイヤー同士でも多様な small gang 編成を組めるようにする）
  - 一方で「勢力ごとの個性」は、得意分野への "ロールボーナス" で表現する
    （例: Compact のロジ艦は repair 効率に補正がつく、
          Nael のタンク艦は特定条件下で装甲/シールド値に補正がつく）
  - ボーナスは「その勢力ならではの強み」であり、
    「その勢力以外ではできないこと」ではない
    → 多様性を損なわず、個性は保たれる
```

各勢力の signature（得意分野）は、その軍事思想・社会構造（`docs/lore/civilizations.md`）
から実際にゲームメカニクスへ落とし込めるものだけを選ぶ。
lore に書かれていても現在のシステムで表現できないもの
（例: Voral Drift の「地形戦術」── Sector に地形概念は存在しない）は
signature から外し、表現可能な側面（フィッティングの改造文化、機動力）に置き換える。

| 勢力 | 全ロールの船を持つ（baseline） | signature（ロールボーナスが付く分野） |
|---|---|---|
| Kaerath Compact | ✅ | ロジスティクス（repair 効率）、組織的フィッティング（標準構成の安定性） |
| Voral Drift | ✅ | タックラー（機動力）、フィッティングの多様性（改造文化による高い構成自由度） |
| Tharren Seekers | ✅ | スカウト（索敵範囲）、EWAR（気脈感知由来のセンサー性能） |
| Nael Sanctuary | ✅ | タンク（防衛特化の装甲/シールド補正）、早期警戒（自陣営内での索敵ボーナス） |

> **注意:** Nael Sanctuary は「攻撃的な遠征軍を持たない」が、
> 「少数精鋭の防衛部隊」（civilizations.md）を持つため非武装ではない。
> 防衛特化のタンク・索敵船にボーナスが乗る、という解釈で船種設計を進める。

#### ロールボーナスの実装方針（將来の `data/*.toml` 拡張のメモ）

```
ロールボーナスは StatDelta / ShipBaseStats のレベルで表現できる
（既存の Fitting システムの延長線上にあり、新しい概念を必要としない）。

例（イメージ。実数値はバランス調整で決定する）:
  Kaerath Compact 製のロジ巡洋艦
    → 同型の他勢力ロジ艦より repair モジュールの効果が高い
  Nael Sanctuary 製のタンクフリゲート
    → 同型の他勢力タンク艦より装甲 / シールド最大値が高いが、速度は低い

これにより「勢力を選ぶ」ことは「使える戦術の幅を狭める」ことではなく
「得意分野の方向性を選ぶ」ことになる。
```

### ❌ 避けるべき悪い点

#### Time Dilation（TiDi）

EVE の**グローバル** TiDi は大規模戦でゲームが 10 倍スローになる。各ノード = 1 コアのため早期かつ広域。

```
このプロジェクトの対応（ADR-0018 で改訂）:
  → INV-TiDi: 論理 Tick は通常一定。過負荷は 分割 → LoD → 局所 TiDi → 入場制限 の順で対処。
    TiDi は全廃せず、分割不能な単一密戦闘の安全網として
    「局所・観測可能・非破壊・自動回復・後置」の条件つきで採用する。
    閾値を EVE より桁違いに高く保ち、出ても当該 Sector 局所・短時間に抑える。
```

> ⚠️ 入場制限そのものが新たな悪用パターンを生む（「人数で埋めて
> 安全圏を作る」）。この問題と対応方針は §8 を参照。

#### 待機時間が多い

ゲート間の移動・スキルトレーニング・製造待ちなど
「待つだけ」のコンテンツが体験を損なう。

```
このプロジェクトの対応:
  - アクティブな操作が常に価値を持つ設計にする
  - パッシブなスキルトレーニングは実装しない
```

#### 初期学習コストが高すぎる

「最初の船を失うのは説明不足のせい」という批判がある。

```
このプロジェクトの対応（進行中）:
  - HP バー・モジュール状態・速度を常時 HUD に表示
  - F1〜F8 のキーバインドを明示
  - シンプルな操作から順番に機能を追加する方針
```

#### Blob 戦争（数が正義）

最大の艦隊が常に勝つ。個人スキルの意味が薄れる。

```
このプロジェクトの対応:
  - 10 人以下の small gang を中核に据え、個人の判断と連携が活きる戦場設計
  - 「数が線形に強さへ変換されない」設計を船種・モジュールの大前提とする
    （詳細な設計原則は §2「Small Gang 思想」参照）
  - 大規模化は Anti-TiDi インフラが整ってから検討（Phase 8）。
    ただし大規模化後も「数が正義」にはしない。
```

#### 情報過多 / UI の複雑さ

新規が圧倒される巨大な UI。

```
このプロジェクトの対応:
  - HUD は段階的に拡張する（現状: HP / 速度 / ロック / モジュール）
  - Cycle ごとに 1 機能ずつ追加する方針
```

## 3. このプロジェクトの優位性

| EVE Online の問題 | このプロジェクトの機会 |
|---|---|
| TiDi（時間停止）| TiDi 閾値を EVE より桁違いに高く・局所/短時間/自動回復に抑えて差別化（ADR-0018） |
| 戦闘の記録が残らない | Event Sourcing で全戦闘が完全に Replay 可能 → 観戦・検証機能 |
| 大艦隊では個人が霞む | 小規模（〜100 隻）に特化し個人の判断が活きる |
| 待機時間 | Tick は通常一定速・リアルタイム（劣化は局所/短時間のみ・ADR-0018） |

## 4. 機能の実装状況

実装済みの機能と、将来検討する機能（未実装）を分けて記載する。
「将来検討する機能」に実装済みが混在すると見分けにくいため、このセクションで分離する
（実装が進むたびに該当項目をここから「4.1 実装済み」へ移すこと）。

### 4.1 実装済み

- **Capacitor（エネルギー管理）** — Phase 6 で実装済み（ADR-0011）。
  Active モジュールが Cap を消費する。Cap が切れるとモジュールが強制 OFF になる。
  「全モジュールを常時 ON にすれば勝ち」にならないバランス調整機能。
  ```
  CapacitorComp.current / ShipStatsComp.cap_max, cap_recharge_per_tick
  ModuleDefinition.cap_cost_per_cycle, cycle_time_ticks（サイクルベース消費）
  Cap は毎 Tick 回復する
  サイクル開始時に cap 不足 → モジュールを強制 OFF（ModuleDeactivated）
  ```
- **Warp** — 実装済み（ADR-0022 intra-Sector Warp）。align → warping 2 フェーズ・W キー。
  移動は `VelocityChanged` で記録し専用イベントは設けない（ADR-0008 の方針）。
- **Tackler（足止め）** — 実装済み（ADR-0024 Fold Disruptor）。`TackledComp` /
  `TackleApplied` / `TackleReleased`・ワープ / ジャンプ拒否。
  Web（速度低下）系はまだ未実装（§4.2 参照）。
- **半自動操船（Approach / Orbit / Keep at Range）** — 実装済み（ADR-0015 / ADR-0031）。
  対象（Ship / Jump Gate）へ接近・指定半径で周回・指定距離を保つ。A / O / K キー、3者は相互排他。
  周回は被弾を減らす戦術として命中式（ADR-0012）と噛み合う。
- **インベントリとランタイム換装** — 実装済み（ADR-0032）。`InventoryComp` / Fit / Unfit。
  スポーン時に全モジュール1個ずつ所持し、いつでもスロットを組み替えられる（I キー）。
- **ローカルリペア（自己修理）** — 実装済み（ADR-0033）。Active な Shield Booster /
  Armor Repairer がサイクルごとに cap を消費して現在 HP を回復（`RepairApplied`）。
  cap を武器 / AB と取り合う判断を生む。**他船への遠隔修理（Logi）は未実装**（§4.2 参照）。

### 4.2 将来検討する機能（優先順位付き・すべて未実装）

### 🔴 近い将来（ゲームバランスの核）

#### Shield リチャージ（非対称 HP 回復）

> 注: これは**時間経過による受動回復**であり、ADR-0033 のローカルリペア（cap を消費する
> アクティブ修理モジュール・§4.1）とは別物。受動リチャージはまだ未実装。

Shield は時間で回復する（Armor / Hull は回復しない）。
この非対称性が「今逃げるか、押し切るか」の判断を生む。

```
設計イメージ:
  毎 Tick: current_shield = min(max_shield, current_shield + recharge_rate)
  recharge_rate は ShipTypeDefinition で定義
  ShieldRechargedイベントは不要（派生状態）、Replay は recharge_rate × ticks で計算
```

### 🟡 中長期（戦術的深みの拡張）

#### ダメージタイプと耐性

EM / Thermal / Kinetic / Explosive の 4 タイプと、各 HP 層への耐性。
「この船にはこの武器が有効」という相性システム。

```
設計イメージ:
  DamageType enum { EM, Thermal, Kinetic, Explosive }
  ShipBaseStats に resistances: Resistances フィールド
  WeaponFired に damage_type を追加
  実ダメージ = damage × (1 - resistance[damage_type])
```

#### リスポーン

破壊後に一定時間後に復帰できる仕組み。
ペナルティ（装備リセット or クールタイム）で「死が怖い」を維持しつつ、
プレイを継続できる。

```
設計イメージ:
  RespawnCommand → 新しい ShipTypeId で spawn_player_ship
  プレイヤーは同じ PlayerId を維持（ship_id のみ変わる）
  フリゲートから始まるリスポーン（装備なし）
```

#### 陣営（Faction）

プレイヤーが陣営を選び、敵対陣営の NPC・プレイヤーと戦う。
「誰と戦うか」の文脈が生まれ、Single Shard の意味が深まる。

```
設計イメージ:
  FactionId を ShipSpawned / PlayerId と紐付ける
  LockSystem: 同一陣営はロック不可
  陣営ポイントで進行度を追跡
```

### 🟢 遠い将来（EVE らしさの完成）

- **Drone**: 船から展開する無人機 — 未実装
- **Logi（修理支援）**: 他の船の Shield を修復するモジュール — 未実装
- **Web（速度低下）**: Tackler（実装済み・§4.1）の隣接機能。速度を落として追走/逃走の
  判断を生む — 未実装

#### ステーション（拠点）— 種だけ・要検討（2026-06-23）

未着手。検討する前に §7 の中心的な問い（「意図的な判断を下す機会を増やすか？」）に
照らして範囲を絞る必要がある。EVE のステーションは複数機能（修理/リフィット・市場・
docking 安全地帯・インダストリー）の複合体だが、そのまま輸入すると「何もせず留まれる
安全な場所」になりやすく、FBD-009 の反グラインド方針（AFK 採掘禁止と同根の懸念）と
相性が悪い。

```
検討の進め方（次にやるなら）:
  1機能だけ選んで小さく定義する。候補:
    - リフィット拠点: フィッティング変更は Sector 内の特定地点でのみ可能
      → 「どこで装備を整えるか」の判断を生む
    - 市場/取引: モジュール・船の売買 → 価格判断・経路選択の判断を生む
    - 安全地帯ではなく「狙われる拠点」: 防衛対象としてのステーション
      （守るか・無視するか、攻めるかの判断を生む。docking 安全地帯にはしない）
  実装コストの見積り（複数機能を同時に検討しない）:
    新 Entity 種別 + Sector 内特別ゾーン処理 + UI が必要、Phase規模の作業
```

優先度: 中長期（戦術的深み拡張）より後ろ。現在ロードマップ未着手の「近い将来」項目
（Shield リチャージ等）が先。ADR 起票は機能を1つに絞ってから（§9 新Crate追加チェック
と同様、範囲を決めてから着手）。

## 5. 実装しない機能（スコープ外）

### スキルポイントは実装しない（非交渉的）

EVE Online のスキルポイント制は**時代遅れの機能**である。

```
問題:
  ゲームの上手さに関係なく、ゲーム時間（またはリアルマネー）の投資量によって
  船の性能・装備の選択肢が変わる。

  具体的に何が起きるか:
    - 1年プレイしたベテランは、どれほど上手い新規プレイヤーでも
      純粋なスタット差で圧倒できる
    - スキルトレーニングを加速するため課金する仕組みが生まれる
    - 「今日から始めた人」と「3年前から始めた人」が公平に戦えない

  これは公平感（Perceived Fairness）を根本から損なう。

このプロジェクトの方針:
  ✓ 全プレイヤーは同じ船・モジュールを最初から使える
  ✓ 強さの差は「どの装備を選んだか」「どう戦ったか」のみ
  ✓ ゲーム時間・課金額は性能に影響しない
```

この原則は**いかなる理由があっても変更しない**。
「やり込み要素」「プレイヤーの成長感」を理由に導入を提案されても実装しない。

代わりに「成長感」を与える方法：
- フィッティングの理解が深まること自体が成長
- 戦闘経験から戦術が洗練されること
- 別の船種・ロールを試すこと

---

### 採掘は実装しない（非交渉的）

EVE Online における採掘は**放置コンテンツ**であり、ゲームプレイとは言い難い。

```
問題:
  採掘とは「採掘レーザーを起動して放置する」行為である。
  プレイヤーが能動的に判断・操作する余地がほとんどない。

  EVE コミュニティでは採掘者は「無力な標的」として語られる。
  これは採掘者自身のコンテンツではなく、
  採掘者を狙う海賊側のコンテンツとして機能している。

  つまり「採掘している人はゲームをしていない」。

このプロジェクトの方針（§7 の設計原則に基づく）:
  「その機能は、プレイヤーが意図的な判断を下す機会を増やすか？」
  → 採掘は No。実装しない。
```

資源・経済が必要になった場合の代替アプローチ（将来の検討のみ）：
- アクティブな操作が必要な「スキャニング」で資源場所を発見
- 発見した資源をめぐる戦闘が主コンテンツ（放置採掘ではなく争奪戦）
- ただしこれも現時点ではスコープ外

## 6. EVE Frontier から学ぶ

EVE Frontier は EVE Online の後継とも言えるプロジェクトであり、
EVE Online の設計を批判的に再解釈している点でこのプロジェクトにも示唆がある。

### 参考になる設計思想

#### 「開発者は舞台だけ提供する」という哲学

```
EVE Frontier: NPCクエストを排除。プレイヤーが互いのコンテンツになる。
              世界のルールと物理だけ開発者が作り、
              その中で何が起きるかはプレイヤーが決める。
```

このプロジェクトとの共鳴：
- Event Sourcing = 「何が起きたか」の完全な記録
  → プレイヤーの行動履歴が世界の歴史になる
- Single Shard = 全員が同じ世界にいる
  → プレイヤーが互いにコンテンツを作り合える
- Anti-TiDi = 世界は通常リアルタイムで動く（劣化は局所・短時間のみ／ADR-0018）
  → 「今ここで起きていること」に意味がある

```
このプロジェクトへの応用:
  NPC の役割 = 「プレイヤーがいない間の世界の動き」を作ること
  NPC はチュートリアル相手・世界に活気を与える存在であり、
  プレイヤーの真の脅威は他のプレイヤーであるべき
```

#### Smart Assemblies（プログラマブルなゲームオブジェクト）

EVE Frontier ではプレイヤーがゲームオブジェクトにロジックを書き込める。
例: 「このドアは XXX コープのメンバーしか通れない」

```
このプロジェクトへの示唆（将来の参考）:
  モジュールの効果が固定値（StatDelta）だけでなく
  条件付きで発動する仕組みへの伏線
  例: 「シールドが50%以下のとき自動で Shield Booster をオンにする」
  → 現状のフィッティング設計はこれを拡張できる構造になっている
```

#### 深刻な死のペナルティ

EVE Online よりさらに厳しい損失設計。「何もかも失う可能性がある」緊張感。

```
このプロジェクトへの応用:
  リスポーン設計で活かす。
  即時復帰より「失うものがある」設計が戦術的判断を生む。
  → docs/design/game-design.md §4 リスポーン設計参照
```

## 8. Sector キャパシティと「安全の購入」問題

### 問題: 入場制限の武器化

INV-TiDi（§2「Time Dilation」参照・ADR-0018 改訂）の下では、過負荷を分割・LoD・局所 TiDi でも
捌けない極端時の**最終バックストップ**として、Sector が負荷上限に達したら新規入場を `SpawnRejected` で拒否する。
これはノード負荷保護という**インフラ側の都合**だが、プレイヤーから見ると
「Sector の人口を定員まで埋めておけば、他のプレイヤーは一切入場できない」
という**完全な防御手段**になる。

```
防衛側が population_cap 分の船（アルト・放置キャラ）を
Sector 内に常駐させる
  → 攻撃側は SpawnRejected を受け取り、入場不可能
  → 当該 Sector は無コストで「絶対安全な領域」になる
```

これは EVE Online で実際に観測された「TiDi の武器化」と同型であり、
技術的な保護機構がゲーム可視のルールになった瞬間、それは必ず
戦術として悪用される。

### 到達点

> **「入場制限」というゲーム可視のメカニクスが存在しないこと自体が理想。**

`SpawnRejected` がプレイヤーに見える限り、悪用は根絶できない。
解決は以下の 3 層の合わせ技で考える。

### 層1: キャパシティの弾性化（Simulation LoD）— 工学的対応

動的分割（空間を細分化してノードを増やす）は「人口が空間的に分散している」
場合の解であって、**密集の解にはならない**。5000 隻の艦隊戦は
1 つのゲート前の半径数 km に集中し、空間をどう切っても全員が同じセルに入る。

密集に効く解は **Simulation LoD（処理忠実度の階層化）**:

```
高忠実度: 交戦中・ロック対象・プレイヤー操作中 → 毎 Tick 完全処理
中忠実度: 近傍にいるが非交戦                    → N Tick に 1 回の物理更新
低忠実度: 放置・遠距離                          → イベント駆動のみ（入力で即昇格）
```

ADR-0008（VelocityChanged）により位置は `position += velocity` の
純粋算術なので、速度が変わらない限り N Tick 分をまとめて積分しても
結果は同一になる（決定論・INV-002 を壊さない）。EVE のグローバル TiDi が
「全員の時間を遅らせる」のに対し、LoD は「判断していない船の計算を
間引く」— 下記 §7 の問いに対する工学側の回答になる。

LoD により population_cap の実効値は桁単位で引き上がり、
`SpawnRejected` への到達頻度自体が激減する。
→ 詳細設計（Tick 処理順序への影響、忠実度の昇格/降格判定）は
専用 ADR で検討する（未作成）。

### 層2: 制約の作中化（diegetic 化）— ゲームデザイン対応

LoD を導入しても物理限界は残る。残った制約は
**インフラの都合ではなくゲーム世界のルールとして見せる**。

**ゲートスループットの世界法則化**:

```
「ジャンプゲートは N 隻/分 しか転送できない」を世界の法則にする
  → 入場拒否ではなく入場キューになる
  → 重要なのは対称性: 防衛側が人数で埋めると、
    自分たちの増援も同じキューに並ぶ
  → インフラ保護が「兵站」という戦略ゲームプレイに変換される
```

**密度への作中コスト**: センサー劣化・範囲攻撃の効率上昇・残骸との
衝突リスクなど、密集自体が戦術的に不利になる要素を設ける。
`SpawnRejected` に到達する前に、ゲームが密集を自発的に抑制する。

判断基準:

> **プレイヤーが回避戦術を考えること自体がゲームプレイになるなら、
> それは悪用ではなくコンテンツである。**

`SpawnRejected` の回避はゲーム外のメタ操作（アルトで埋める）だが、
ゲートキューの攻略は兵站という正当な戦略である。

### 層3: 設計原則 — GD-INV-001「安全は購入できない」

> **GD-INV-001: いかなる領域も、継続的なコスト（人の注意・操作）を
> 払い続けない限り安全であってはならない。**

EVE Online が学んだ教訓は「絶対安全圏を作るとそこに経済と人口が
吸い込まれ、リスクある空間 = コンテンツが死ぬ」だった。
この原則は INV-001〜006（AI_DEVELOPMENT_GUIDE.md「Architecture Invariants」・技術的不変条件）と対をなす
**ゲームデザイン不変条件**であり、§7 の問いと並んで、将来のあらゆる
機能提案（構造物・防衛設備・新たな保護メカニクスなど）を審査する基準とする。

### 最終バックストップ（生カウント）— ✅ 実装済み（8B-1）

過負荷は分割 → LoD → 局所 TiDi の順で捌き（ADR-0018）、それでも実時間遅延が
許容域を超える極端時のみ新規入場を絞る。その最終バックストップを最小実装する。

```
- at_population_cap() = ship_count() >= population_cap
- TiDi 予算（DilationController）と同じ単位（生のエンティティ数）で揃える
- population_cap は既定 100,000（TiDi 閾値より桁違いに高い）。--pop-cap N で可変
- 両 serve ループで、cap 到達時は新規接続を spawn 前に拒否する
- 強制退去はしない（在席中の船は数えるだけ。INV-002 と無関係）
```

**実装（`dawn-simulation/node.rs`）**: `at_population_cap()` は生の `ship_count()` を
`population_cap` と比較するだけ。`--pop-cap N` で Sector 毎に可変。

> **却下した案: 「アクティブ船除外（実効人口）」**
> 当初は「直近 300 Tick 操作のない船を数えない」案を実装したが撤回した。
> サーバが観測できるイベントから「在席して静観中」と「AFK」は区別できず、
> 何より **INV-MOVE（ADR-0008）により等速移動する船はイベントを出さない** ため、
> 「無イベント = idle」が成立しない（隊列で等速移動する艦隊が誤って idle 判定され、
> 実際には配信帯域を食う）。被弾（DamageTaken）が AFK 船を「アクティブ」にする逆方向の
> 誤りもある。放置船を安くする効果は「数から除外」ではなく **層1 の LoD（8B-3）で
> 忠実度を下げて 1 隻あたりのコストを下げる** ことで表現する。結果として TiDi の
> 発動頻度が下がる形で効き、生カウントのバックストップはあくまで予測可能な最終手段に保つ。

### 却下した代替案

| 案 | 却下理由 |
|---|---|
| 動的分割のみ | 密集（1点への集中）に空間分割は原理的に無力（層1） |
| 交戦目的の予約枠 | 偽装交戦という新たな悪用面を生む。層2 のゲートキューが対称性で同じ目的を達成 |
| グローバル TiDi（EVE 型・全 Sector 一律） | 早期広域の TiDi は却下。dawn は局所・最終手段の TiDi のみ採用（ADR-0018） |
| 非アクティブ船の強制 Despawn | 新規 Event（`ShipDespawnedDueToInactivity`）が必要で INV-002 確認コストが大きい |
| Sector 滞在への資源コスト | 経済システム未実装で当面は実装手段がない（FBD-008 は ADR-0016 で撤廃済み） |
