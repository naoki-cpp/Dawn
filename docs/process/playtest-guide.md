# Playtest Guide

## 1. このドキュメントの目的

Phase 6 の主目標は「ゲームが実際に面白いか」を人間から検証することである。

> **開発の最大リスクはもはや技術的ではない。**
> 「現在のゲームループが楽しいか」が次の最大リスクである。

このドキュメントは以下を定義する。

- プレイテストの実施方法
- 自動収集すべきメトリクス
- セッション後に確認すべき質問
- バランス問題を示すシグナル
- Phase 7 着手の「十分に面白い」基準

---

## 2. プレイテスト前の前提条件

### 死亡処理の方針

「死亡後にプレイを継続できる仕組み」は **デュエルモード** で解決する。

```
採用しない: リスポーン / 脱出ポッド（ADR-0010: deferred）
  → テスト用にプロダクションコードを変更することになる
  → 宇宙ゲームとしても「その場で復活」は不自然

採用する: デュエルモード（片方が死んだら終了）
  → 既存メカニクスのみで完結
  → 「1戦の中での判断」を純粋に検証できる
  → セッション = 複数回のデュエルを繰り返す形式
```

### デュエルモードの前提条件

```
[実装済み] InitialState にプレイヤー船識別フラグ（is_player）
  → Godot が「相手プレイヤーの船」と NPC を区別するために使用
  → node.rs の build_initial_state_json() が is_player を出力する

[必須] Godot に勝敗画面を追加
  → ShipDestroyed 受信時に自分/相手の船かを判定して表示
  → main.gd の変更のみ

[実装済み] デュエルメトリクスの stdout 出力 + JSON ファイル出力
  --duel モード限定。ShipDestroyed 発火時に以下をコンソールへ出力する:
    - 勝敗（Player Win / Bot Win）
    - 経過 Tick 数
    - 船ごとの cap 枯渇（強制 OFF）回数
  同時に `data/session_duel_<unix秒>.json` へ同内容を書き出す
  （複数セッションを横断した集計・分析を可能にするため）。
  詳細集計（§6 のロックオン/モジュール/フィッティングメトリクス）は将来拡張予定。
  → dawn-simulation/src/serve/mod.rs の DuelMetrics::write_json_summary() 参照
```

## 3. セッション構成（3〜10人・約60分）

### フェーズ1 — チュートリアル（10分）

観察者（開発者）が口頭で以下を説明する。

```
- 左ドラッグでカメラを回転（軌道視点操作。キー操作ではなくマウスドラッグのみ）
- 左ダブルクリックで移動（推力方向の指定）
- 左シングルクリックで船 / ジャンプゲートを選択（接近対象の指定・ADR-0015）
- A キーで選択した船 / ゲートへ半自動接近（Move / Stop で解除。ゲートは起動半径内で停止）
- W キーで選択したゲートまたは天体（惑星のみ。恒星は実体メッシュを撤廃したためクリック選択・
  ワープ対象にできない——空シェーダーの方向ベース描画のみで表現する）へワープ（短距離 Fold =
  高速移動・ADR-0022/0025）。
  EVE 準拠で、まず最大速度の 75% までターゲット方向へ整列加速してから warp 速度で圏内へ。
  整列は船の機動性次第（鈍い船ほど長い）。整列中は Move / Stop で中断できるが、warp に入ると終点まで止まれない。
  3,000u 未満のゲートには近すぎてワープできない＝接近を使う。天体は radius×1.5 の地点に到着する。
  クリックでゲート / 船 / 惑星を選択し、W で対応するワープを実行できる）
- O キーで選択した船 / ゲートの周りを周回（Orbit）。半径は省略時、武器射程
  （未装備なら既定値）。命中率式（ADR-0012）はトランスバーサル速度が高いほど被弾しにくい
  ため、オービット自体が回避手段になる（ADR-0031）
- K キーで選択した船 / ゲートから指定距離を保つ（Keep at Range）。近すぎれば
  真っ直ぐ離れる方向へ、遠すぎれば対象へ向けて詰める、指定距離付近では停止保持
  （ADR-0031）。Orbit と異なり周回しない（純粋なスタンドオフ）
- [ / ] キーで K の保持距離を 1km 刻みで調整（既定 10km、1〜200km）。HUD に現在値が
  表示される。武器射程に応じて適切な距離はターゲットごとに変わるため、サーバ側の
  既定値に任せず自分で選ぶ
- Approach（A）/ Orbit（O）/ Keep at Range（K）は互いに排他——後から出したコマンドが
  前の操船モードを上書きする。Move / Stop でも解除できる
- S キーで減速停止（逆推力をかけて速度ゼロまで減速）
- 右クリックでロックオン開始
- F1〜F8 でモジュールの ON/OFF（HUD 下部のモジュールバーをクリックしても同様に切り替えられる）
- I キーでインベントリ / 換装パネルの表示切替（ADR-0032）。左に現在の装備、
  右に未装備のインベントリが並ぶ。インベントリの行をクリックすると即座にその
  モジュール自身のスロット種別へ装備（スロット選択は不要）、装備中の行をクリック
  すると外してインベントリへ戻す。プレイヤーはスポーン時に登録済みモジュール
  全種を1個ずつ所有（補充なし）。換装はいつでもどこでも可能
- Tab キーでタクティカルオーバーレイ表示 / 非表示（緑: 最適射程 / 橙: フォールオフ境界）
- J キーでジャンプゲート使用（選択中 or 近接中のゲートへ。圏外（activation_radius=2,000u 超）なら
  まず自動ワープ（3,000u 以上離れていれば）、ワープにも近すぎる 2,000〜3,000u の帯では自動接近に
  切り替えてからジャンプする・ADR-0022。圏内に入ったら再度 J を押す。
  HUD に「[J] Jump Gate」と表示される）
  ※ ジャンプは `--serve --cluster`（3ノード Raft クラスタ）でのみ有効。
    単一 Sector の `--serve` では無効。
- **移動ループ（クラスタモード）**: プレイヤーは Sector 原点付近（30,000, 0, 0、恒星から十分離れた安全距離）にスポーンする。
  Gate 0（x=600,000 付近、Sector の縁）のリングをクリックで選択 → **W でワープ**（または A で接近）→
  ゲート圏内に着いたら **J でジャンプ**。HUD に選択ゲートと「[W] Warp」/「[W] too close to warp」が出る
  （ゲートが 3,000u 未満だと近すぎてワープ不可・接近を使う）
- HP バーの 3 層（シールド / アーマー / ハル）の意味
```

説明後、NPC のみの環境で 5 分間自由に動く時間を与える。
観察者はこの間に「何を見て / 何を押しているか」を記録する。

### フェーズ2 — 対 NPC 戦（15分）

NPC Frigate × 20 を配置した状態でプレイヤーが自由に戦う。
観察者は介入せず、詰まったときのみ質問に答える。

確認ポイント:
- フィッティング選択の理由（何を考えて装備を決めたか）
- モジュール操作のタイミング（F キーをいつ押しているか）

### フェーズ3 — PvP 混在（20分）

NPC + プレイヤー全員が同じ空間に配置する。

セッション 1〜2 は「NPC が敵、プレイヤーは協力」として開始する。
「誰を攻撃するか」が不明瞭になる可能性があるため、
最初に陣営の文脈なしで PvP を強制しない。

セッション 3 以降は全員中立（自由に攻撃可）にして PvP の反応を測定する。

### フェーズ4 — 振り返り（15分）

§5 の質問リストを使ったディスカッション。
録音または文字起こしを行う。

## 4. セッションシリーズの計画

| セッション | 変更点 | 主な目的 |
|---|---|---|
| Session 1 | 変更なし（ベースライン） | 現状の問題点をすべて観察する |
| Session 2 | `data/ship_types.toml` を Session 1 の結果をもとに調整 | バランス変更の効果を測定する |
| Session 3 | PvP フェーズを早める（フェーズ2 直後に混在） | 対人戦への反応を測定する |

各セッションの結果は §8 の結果記録フォーマットに残す。

## 5. セッション後の質問リスト

### 理解度の確認

```
「ロックオンとは何をしていると思いましたか？」
「モジュールの ON/OFF は何を変えていると思いましたか？」
「HP が 3 層（シールド・アーマー・ハル）あることに気づきましたか？」
```

### 判断の意味についての確認

```
「どの船を選びましたか？ その理由は？」
「戦闘中に一番困った瞬間はいつですか？」
「逃げようと思った瞬間はありましたか？ 実際に逃げられましたか？」
「相手の行動に対して自分の行動を変えましたか？ どう変えましたか？」
```

### フィッティングについての確認

```
「装備を決めるとき何を考えましたか？」
「使わなかったモジュールはありましたか？ なぜ使いませんでしたか？」
「次プレイするなら装備を変えますか？ どう変えますか？」
```

### 体験全体の確認

```
「一番面白かった瞬間を教えてください」
「一番わからなかったことは何ですか？」
「もう一度プレイしたいと思いますか？」（Yes / No）
```

## 6. 自動収集すべきメトリクス

`dawn-simulation` に `MetricsCollector` を追加し、
セッション終了時に `data/session_YYYYMMDD_HHMMSS.json` へ書き出す。

### 戦闘メトリクス

```
engagement_duration_ticks   — TargetLocked → ShipDestroyed の Tick 数
kill_count_by_ship_type     — ShipTypeId 別の撃墜数
death_count_by_ship_type    — ShipTypeId 別の被撃墜数
damage_dealt_by_ship_type   — DamageTaken.damage の ShipTypeId 別合計
first_kill_tick             — セッション開始から最初の ShipDestroyed までの Tick 数
```

### ロックオンメトリクス

```
lock_attempt_count          — LockOnCommand の発行数
lock_success_count          — TargetLocked の発行数
lock_broken_count           — LockLost の発行数（ターゲットが逃げた）
lock_success_rate           — lock_success / lock_attempt
```

### モジュールメトリクス

```
module_activation_by_id     — ModuleActivated の module_id 別集計
module_never_used_ids       — 一度も Activate されなかった module_id の一覧
active_module_on_rate       — ModuleActivated / (ModuleActivated + ModuleDeactivated)
```

### フィッティングメトリクス

```
fitting_diversity_index     — セッション中にプレイヤーが選んだ装備パターンの種類数
player_ship_type_choice     — 各プレイヤーが選んだ ShipTypeId の分布
```

### 全体

```
session_duration_ticks      — セッション全体の経過 Tick 数
total_events_per_tick       — Tick あたりのイベント数（負荷確認）
```

### ロギング要件

```
必須（現在ない）:
  - 各 DomainEvent にリアルタイムスタンプ（wall clock）を付与してログファイルに書く
    ※ 因果順序には Tick を使い続ける（INV-005）
    ※ リアルタイムスタンプはセッション分析専用
  - 接続・切断イベント（PlayerId, wall clock）
  - コマンド受信ログ（PlayerId, CommandType, ship_id, tick）

推奨:
  - Tick SLA 超過ログのファイル書き出し確認
  - セッション開始時のフィッティング選択ログ

不要:
  - 毎 Tick の Position ログ（ADR-0008: 位置は派生状態）
  - ダメージ計算の中間値
```

## 7. バランス問題のシグナル

### 船バランス

```
[危険] 1 つの ShipTypeId が全 kill の 70% 以上を占める
  → その船が強すぎる。max_speed か weapon_damage を下げる。

[危険] 1 つの ShipTypeId の death_count が 0
  → その船が死なない。HP を下げるか速度を調整する。

[警告] Player Frigate の engagement_duration が Player Cruiser の 1/5 以下
  → Frigate が即死している。HP 差が大きすぎるか Cruiser の lock_time が短すぎる。

[警告] プレイヤー全員が同じ ShipTypeId を選ぶ
  → 船種の差別化が機能していない。

[情報] kill が session 開始後 5 分以上ゼロ
  → 全員が遠距離で睨み合っているか、ダメージが足りない。
```

### 戦闘設計

```
[危険] engagement_duration_ticks の中央値 < 30 tick（3秒）
  → 「気づいたら死んでいた」。プレイヤーが判断する時間がない。
  → weapon_damage_add を下げるか max_shield を上げる。

[危険] engagement_duration_ticks の中央値 > 600 tick（60秒）
  → 戦闘が長すぎて退屈。ダメージが足りないか逃げが強すぎる。

[危険] lock_success_rate < 30%
  → ロックが成立する前に相手が逃げる。lock_time か速度差を見直す。

[警告] 振り返りで「ロックオンに気づかなかった」という回答が複数
  → Godot 側の視覚フィードバックが不足している。

[警告] lock_broken_count / lock_success_count > 50%
  → 「逃げ」が支配的な戦術になっている。意図的かどうかを PvP セッションで確認する。
```

### フィッティング設計

```
[危険] module_never_used_ids にほぼ全モジュールが入っている
  → F1〜F8 のキーバインドに気づいていない可能性。チュートリアルを強化する。

[危険] 全プレイヤーのフィッティングが同一（fitting_diversity_index = 1）
  → 最適解が 1 つしかない。モジュール / 船種バランス（data/*.toml）を見直す。

[警告] active_module_on_rate > 95%
  → 全モジュールを常時 ON にしている。「ON にし続ければ勝ち」になっている。
  → cap コスト（cap_cost_per_cycle）が軽すぎる。data/modules.toml を見直す。

[警告] 振り返りで「装備を変えたい」という回答が 0
  → フィッティングが意思決定の要素になっていない。

[情報] 10MN Afterburner が一度も使われない
  → 大型推進モジュールの価値が伝わっていない。
```

## 8. Phase 7 着手の「十分に面白い」基準

技術的条件ではなく、**観察によって確認する条件**として定義する。

### 必須条件（全て満たすこと）

```
[戦術判断の証拠]
  振り返りで「〜だったから〜した」という因果のある判断を
  少なくとも 2 名のプレイヤーが語れる。

[再プレイ意欲]
  「もう一度プレイしたいか」に 3 名以上が Yes と答える。

[フィッティングの多様性]
  同一セッション内で異なるフィッティングのプレイヤーが 2 名以上いる。
  （fitting_diversity_index ≥ 2）

[戦闘時間の許容範囲]
  engagement_duration_ticks の中央値が 30〜600 tick の範囲内。

[リスポーン後の継続]
  死亡したプレイヤーがリスポーン後も戦闘に戻ってくる。
  セッション中に自発的に離脱しない。
```

### 十分条件（いずれか 1 つで Phase 7 着手を正当化できる）

```
プレイヤーが自発的に戦術を話し合う（「次はこうしよう」「あの装備が強い」）
プレイヤーが特定の船・フィッティングへの対策を考え始める
セッション外でゲームの話をし始める
```
