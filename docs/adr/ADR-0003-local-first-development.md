# ADR-0003 — Local-First Development（段階的分散化）

## コンテキスト

分散シミュレーション基盤を構築するにあたり、  
「最初から分散構成で開発するか」「まずローカル完結で動かすか」の選択を迫られた。

最終目標は複数ノードの物理分散だが、  
最初のフェーズで何を実装するかを決定する必要があった。

---

## 現在の制約（意図的に採用しているもの）

以下の制約は「技術的にできないから」ではなく「今は必要ないから」採用している。

```
- Single Process のみ
- ネットワーク通信なし（gRPC / QUIC 不使用）
- 分散コンセンサスなし（Raft 不使用）
- CRDT なし
- コンテナなし（Docker / Kubernetes 不使用）
- ノード間通信は In-Memory Channel のみ
```

これらの制約を解除するには新しい ADR を起こして人間の承認を得ること。  
AI エージェントが独自の判断でネットワークコードを追加してはならない。

---

## 検討した選択肢

### A: 最初から分散構成で開発する

gRPC / Raft / Docker を最初のフェーズから導入する。

**メリット:**
- 将来の移行コストがゼロ
- 分散特有のバグを早期に発見できる

**デメリット:**
- ドメインロジック（Ship の移動・イベント生成）が正しく動く前に
  ネットワーク層のデバッグが必要になる
- 「ネットワーク障害のせいか、ドメインロジックのバグか」の切り分けが困難
- テストの複雑性が最初から高くなり、AI による継続開発が困難になる
- 開発環境のセットアップコストが高い

### B: Local-First（段階的分散化）

まずローカル完結で正確なドメインロジックを確立し、
ネットワーク層を後から差し込む。

**メリット:**
- ドメインロジックの正しさを確認してから複雑性を追加できる
- テストが単純（ネットワークのモックが不要）
- `cargo test` だけで開発サイクルが完結する
- In-Memory Channel と gRPC の差し替えを `trait` の抽象化で実現できる

**デメリット:**
- 将来の移行時に抽象化層の追加が必要
- 分散特有のバグ（ネットワーク分断・タイミング問題）は後のフェーズまで発見できない

---

## 決定

**Local-First 開発を採用する（選択肢 B）**

---

## 根拠

ドメインロジックの正しさ（Ship が正しく動き、Event が正しく記録される）を  
先に確立することが最重要課題である。  
ネットワーク層は「正しく動くドメインロジックを複数ノードに展開する」という  
後から追加できる外層として設計する。

この判断は EVE Online の開発経緯とも一致する。  
大規模分散システムは「動く小さいシステム」から段階的に育てたものが成功している。

AI エージェントによる継続開発を前提にすると、  
テストが単純であることは特に重要である。  
ネットワークのモックが不要なテストは、AI が生成したコードの品質を  
`cargo test` だけで即座に確認できる。

---

## 影響

### この決定が保証するもの

```
- Phase 0–1 のコードにネットワーク依存は一切含まれない
- `cargo test --workspace` が Docker 等の外部サービスなしで通過する
- 全ての並行処理は In-Memory Channel で完結する
```

### 分散化への移行戦略

抽象化境界を今から正しく設計することで、将来の移行コストを最小化する。

```
現在（Phase 0–1）         将来（Phase 4 以降）
────────────────────      ────────────────────
In-Memory Channel    →    gRPC / QUIC
Tick::ZERO ベース    →    VectorClock
SimulationNode       →    SectorSimulatorActor
InMemoryEventStore   →    ファイルベース EventStore → 分散 EventStore
```

各移行ポイントで対応する `trait` が差し替え可能になっていること:

```
EventStore trait  : InMemoryEventStore → FileEventStore の差し替えを許容
（将来）Channel trait: mpsc → gRPC Channel の差し替えを許容
```

### この決定が強制する設計上の制約

```
- Phase 0–1 の Cargo.toml に tonic / reqwest 等を追加してはならない
- ノード間通信が必要に見える処理も In-Memory Channel で実装する
- 「ネットワークがないと動かない」コードを書いてはならない
```

---

## 今後の再評価トリガー

- Single Process では達成できないスケール要件（エンティティ数・Tick 速度）が生じた場合
- In-Memory Channel の実装が物理ネットワークと著しく異なる挙動を持つことが判明した場合
